## Findings this run

### F-001 — bug — open
**Location:** `graphwerk/session.py::SessionRunner.status` / `_settle`
**Evidence:** `status()` is called from `GET /api/session` (polled every
1.5s by every open browser tab) and from `POST /api/prompt` via `start()`.
FastAPI runs these sync endpoints in a threadpool, so with two clients —
the documented setup is exactly that: the user browses from another LAN
device, often alongside a local tab — two threads can call `status()`
concurrently. At the moment the child exits, both threads can observe
`self._child.poll()` returning a non-None exit code before either has run
`_settle()`; both then enter `_settle()`, the first closes
`self._child_output` and sets it to `None`, and the second crashes on
`self._child_output.seek(0)` (`AttributeError: 'NoneType' object has no
attribute 'seek'`) → 500 on `/api/session` right when the session
finishes, and the runner's state can settle inconsistently. No lock or
idempotence guard exists anywhere in the class.
**Ticket:** docs/tickets/086-sessionrunner-settle-race.md

### F-002 — bug — open
**Location:** `graphwerk/rationale/transcript.py::_bash_deleted_rel_paths`
**Evidence:** absolute path tokens are normalized through `_to_staged_rel`,
but relative tokens are kept verbatim (`rel_path = token`). A deletion like
`rm ./old.py` — a very common agent command shape — produces an
`EditEvent(rel_path="./old.py")`, which never matches the differ's node id
`old.py`. The deleted file therefore never enters the `rel_paths` set that
`attribute_files` scans, nor the proximity fallback — silently
reintroducing exactly the ADR 026 gap this code was added to close, for
any `rm`/`git rm` invocation that isn't already a clean staged-relative
path (`./x`, `a/../b.py`, paths relative to a subdirectory the agent
`cd`-ed into). Deletion *bullets* (the primary path) still work; the
mention/proximity backstop doesn't.
**Ticket:** docs/tickets/087-normalize-bash-deletion-paths.md

### F-003 — inconsistency — open
**Location:** `docs/decisions/016-call-edge-status.md` +
`docs/tickets/049-call-edge-status-model.md` vs
`graphwerk/service.py::_mark_edge_status`
**Evidence:** ADR 016 decision #1 and ticket 049's acceptance criteria both
specify that a `calls` edge from an `AFFECTED` source into an `UNCHANGED`
target gets `status = AFFECTED`. Commit cfb4832 deliberately removed that
branch as an over-tagging bug ("any call from an affected node into
unchanged code was tagged affected, even calls with no bearing on the
change") and pinned the new behavior with
`test_calls_edge_to_unrelated_target_from_affected_source_has_unchanged_status`
— but the deviation is recorded only in the commit message and the
function docstring. The ADR and the (done) ticket still state the old
rule, so anyone auditing code against docs finds a false contradiction.
The **doc side is wrong**: amend ADR 016 with a supersession note and fix
ticket 049's criteria to match shipped behavior.
**Ticket:** docs/tickets/088-record-shipped-deviations-adr-016-020.md

### F-004 — inconsistency — open
**Location:** `docs/decisions/020-edge-hover-reveal-and-zoom-feel.md` +
`docs/tickets/058-wheel-zoom-feel.md` vs `static/app.js:280`
**Evidence:** ADR 020 and ticket 058 say `wheelSensitivity` is *lowered*
from `0.3` ("start around 0.15–0.2 ... so a single wheel notch moves
less"). The implementing commit (78b4370) set it to `5` — the opposite
direction, ~16× faster — with no recorded reason; `minZoom`/`maxZoom`
landed as specified. The ticket is marked done and UI changes are
user-eyeballed, so the shipped value was most plausibly tuned up by feel —
making the **doc side wrong** — but nothing records that. The ticket
should confirm the value is intentional and amend ADR 020/ticket 058 (or
restore a low value if `5` was a leftover experiment).
**Ticket:** docs/tickets/088-record-shipped-deviations-adr-016-020.md
