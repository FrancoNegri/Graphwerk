# 037. Bottom session bar: commit message + commit-all / discard

Status: proposed
Date: 2026-07-17

## Context

ADR 011 pulled the prompt box forward so the whole flow — ask, watch the
graph fill in, review — happens in one place (docs/04, Phase 3 note). But
the flow still has no ending. After reviewing, the developer either applies
files one by one and then switches to a terminal to `git commit`, or
abandons the change set with manual git surgery in the worktree. Phase 2's
exit criterion is dogfooding graphwerk on its own features; a dogfood loop
that ends with "now go do git things elsewhere" isn't closed.

The user's call (2026-07-17): dock the prompt bar at the bottom of the
screen and grow it into a session bar — a text box that fills with a
commit message for the staged change set once the agent session completes
(autogenerated by Claude, editable by the reviewer), plus two buttons:
**commit** everything to the source repo with that message, and **discard**
everything, returning the staging area to zero.

## Decision

Four pieces, smallest coherent versions:

1. **Placement.** The prompt bar moves from under the header to a bar
   docked at the bottom of the viewport. Pure presentation
   (`index.html` / `style.css`).

2. **Commit message, mined not requested.** `SESSION_GUIDANCE` (ADR 012)
   gains one more instruction: after the per-file summary bullets, end
   with a single line `Commit-message: <one-line conventional summary>`.
   The rationale layer parses that line from the transcript's final
   assistant segment (same machinery as bullet mining, ADR 006/025) and
   exposes it; the snapshot carries it in `meta`. The UI fills the text
   box with it when a session completes; the reviewer edits freely. If no
   line is found (foreign session, uncooperative agent), the box stays
   empty with a placeholder — manual typing is the fallback.

3. **Commit-all: `/api/commit`.** Takes the (possibly edited) message.
   Applies every changed file in the current change set to the base tree
   via the existing file-level apply, then runs `git add -- <those paths>`
   and `git commit -m <message>` in the base repo (stdlib `subprocess`).
   The add is scoped to the applied paths so a dirty base tree's unrelated
   files are never swept into the commit. Fails with a clear error —
   before applying anything — when the base tree is not a git repository
   (the scripted demo trees) or the message is empty.

4. **Discard: `/api/discard`.** Reverse-applies the current change set
   onto the staging tree: added files are deleted, modified and deleted
   files are restored from base. Refused (409) while a session is running,
   so files are never yanked out from under a live agent. After discard,
   the graph naturally re-renders clean via the existing hash polling.

## Alternatives considered

- **Commit message via a second `claude -p` call after the session** —
  truly on-demand generation, but costs a whole extra headless session
  (latency + tokens) per prompt, needs busy-state plumbing alongside
  `SessionRunner`, and duplicates knowledge the transcript already
  contains. Mining the wrap-up is free and uses existing machinery.
- **Commit message derived deterministically from rationale bullets** —
  no new guidance, but produces a bullet dump, not a commit message, and
  isn't what was asked ("autogenerated by claude"). Kept only as the
  spirit of the empty-box manual fallback.
- **Discard via `git checkout -- . && git clean -fd` in the worktree** —
  handles non-Python files too, but `clean -fd` would also delete
  untracked files the agent legitimately created for itself (settings,
  scratch), does nothing for the non-git demo trees, and discards more
  than the graph showed the reviewer. Reverse-applying the computed
  change set discards exactly what was on screen, in both demo and
  worktree setups.
- **Commit via `git commit -am`** — sweeps unrelated pre-existing dirty
  files in the base tree into the reviewer's commit; scoped `git add`
  avoids it.

## Consequences

- The dogfood loop closes: prompt → review → apply/reject per node, or
  commit/discard the whole set — all in one screen. Directly serves
  Phase 2's exit criterion.
- First git invocation in the codebase (stdlib subprocess; no new deps).
  The base tree being a git repo becomes a soft requirement — only for
  the commit button, everything else still works without it.
- Discard shares the change-set enumeration with the differ, so it
  inherits ticket 009's known limitation: non-Python staged changes are
  invisible and hence not discarded. Same gap, same fix later.
- The session bar overwrites the message box only when a *new* session
  completes (tracked by session id), so polling never clobbers the
  reviewer's edits.
- Invariants touched: none violated. The agent keeps its real worktree;
  discard is an explicit reviewer action, blocked while the agent runs.
  Logic stays in Python; `app.js` consumes `meta.commit_message` and posts
  to two endpoints.

## Out of scope

- Reject/resume into the live session — Phase 3, unchanged.
- Partial commit (subset of nodes) — apply-per-node already covers it;
  grouped selection belongs with Phase 4's apply-group work.
- Committing or branching inside the *worktree*, or any branch strategy
  in the base repo — the commit lands on whatever branch base has
  checked out.
- Regenerate-message button (re-ask Claude after edits) — revisit if the
  mined line proves weak in dogfooding; would then use the second-call
  alternative above.
- Non-Python files in commit/discard — blocked on ticket 009's differ
  work, not on this ADR.
